# Правила разработки Backend (Fintech)

Этот документ описывает строгие инженерные стандарты для разработки backend-части нашего финтех-сервиса. В финтехе цена ошибки — реальные деньги и репутация, поэтому мы руководствуемся паранойей, точностью и отказоустойчивостью.

## 1. Работа с деньгами и транзакциями (Core Ledger)
- **Исключительно точные типы:** Для любых денежных сумм используйте только `Decimal` (Python) или `BigDecimal` (Java/JS). Никогда не используйте `float` или `double`. Всегда явно указывайте точность округления (например, `ROUND_HALF_EVEN` — банковское округление).
- **Append-Only Ledger (Двойная запись):** Финансовые транзакции не обновляются и не удаляются. Баланс — это всегда производная (сумма) от всех исторических записей (ledger entries). Если нужно отменить транзакцию, создается новая компенсирующая транзакция (Reversal).
- **Конечные автоматы (State Machines):** Жизненный цикл любой транзакции (платеж, вывод, пополнение) должен строго контролироваться конечным автоматом (например: `PENDING` -> `PROCESSING` -> `COMPLETED` / `FAILED`). Запрещены прямые переходы из `PENDING` в `REFUNDED` минуя `COMPLETED`.
- **Идемпотентность:** Все мутирующие API-запросы (`POST`, `PUT`, `PATCH`) обязаны принимать заголовок `Idempotency-Key`. При повторном запросе с тем же ключом сервер должен возвращать закэшированный результат предыдущего успешного ответа, не выполняя операцию повторно.

## 2. Базы данных и Конкурентность
- **Блокировки (Locking):** При обновлении балансов или статусов транзакций обязательно используйте пессимистичные блокировки (`SELECT ... FOR UPDATE`) или оптимистичные блокировки (версионирование строк), чтобы избежать состояния гонки (Race Conditions).
- **Уровни изоляции:** Для критических финансовых операций используйте уровень изоляции транзакций `REPEATABLE READ` или `SERIALIZABLE`.
- **Soft Deletes:** Физическое удаление записей (`DELETE`) из критических таблиц (пользователи, счета, транзакции) строго запрещено. Используйте флаг `is_deleted` или `deleted_at`.

## 3. Интеграции с платежными шлюзами и внешними API
- **Circuit Breaker & Retries:** Внешние сервисы (банки, шлюзы, KYC-провайдеры) могут падать. Оборачивайте все вызовы в паттерн Circuit Breaker. Реализуйте повторные попытки (Retries) с экспоненциальной задержкой (Exponential Backoff) и Jitter, но **только для идемпотентных запросов**.
- **Таймауты:** Ни один сетевой вызов не должен выполняться без явно заданного таймаута (Connect Timeout и Read Timeout).
- **Валидация Webhooks:** Все входящие вебхуки от платежных систем должны строго верифицироваться (проверка подписи/HMAC, проверка IP-адресов отправителя).
- **Dead Letter Queues (DLQ):** Все фоновые задачи (очереди), которые не удалось выполнить после серии попыток, должны отправляться в DLQ для ручного разбора инженерами.

## 4. Безопасность и Комплаенс (Security & Compliance)
- **Маскирование PII и PCI-DSS:** В логах, трейсах и дампах памяти никогда не должны появляться: полные номера карт (PAN), CVV, пароли, токены, полные паспортные данные. Маскируйте их на уровне middleware/логгера (например, `4532 **** **** 1234`).
- **Шифрование:** Чувствительные данные в БД (например, токены доступа к банкам) должны храниться в зашифрованном виде (Encryption at Rest).
- **Rate Limiting и Throttling:** Все публичные API должны быть защищены от брутфорса и DDoS с помощью строгих лимитов запросов (по IP, по User ID, по эндпоинту).
- **Принцип наименьших привилегий:** Сервисы и скрипты должны иметь доступ только к тем таблицам и операциям в БД, которые им абсолютно необходимы.

## 5. Наблюдаемость (Observability)
- **Correlation ID (Trace ID):** Каждому входящему HTTP-запросу должен присваиваться уникальный `trace_id` (и `span_id`), который прокидывается во все логи, фоновые задачи и исходящие запросы к внешним системам. Это критически важно для расследования инцидентов.
- **Структурированное логирование:** Логи должны писаться строго в формате JSON (JSON lines) в stdout/stderr. Используйте `loguru` с перехватом стандартного `logging` (`InterceptHandler`).
  - Обязательные динамические поля (`trace_id`, `span_id`, `user_id`, `ip`) должны прокидываться через `ContextVar` (`trace_context`) и автоматически добавляться в payload каждого лога.
  - Встроена автоматическая маскировка секретов (токенов, паролей) через регулярные выражения (fallback sanitization).
  - Строгое ограничение размера сообщений и трейсов исключений (в байтах) для защиты сборщиков логов (Loki/Docker).
  - Частые эндпоинты (health/metrics) должны фильтроваться из access-логов.
  - Для сторонних библиотек (например, `httpx`, `httpcore`) уровень логирования должен быть повышен до `WARNING`.
- **Алертинг на аномалии:** Код должен экспортировать метрики (например, Prometheus). Резкий всплеск `FAILED` транзакций или падение конверсии успешных платежей должно немедленно вызывать алерт.

## 6. API и Валидация
- **Строгая валидация контрактов:** Используйте строгие схемы (например, Pydantic) для валидации всех входящих данных. Неизвестные поля должны отбрасываться или вызывать ошибку валидации.
- **Версионирование:** Любое изменение контракта API, ломающее обратную совместимость, должно выпускаться в новой версии API (например, `/v2/payments`).
- **Стандартизация ошибок:** API должно возвращать стандартизированный формат ошибок (RFC 7807 Problem Details). Никогда не возвращайте stack trace клиенту.

## 7. Архитектура и структура проекта (Domain-Driven Design)

Мы используем доменную (Feature-Sliced) архитектуру. Она обеспечивает высокую связность (High Cohesion) внутри модулей и слабую зацепленность (Low Coupling) между ними, что идеально подходит для масштабируемого финтех-проекта на стеке FastAPI + asyncpg + SQLAlchemy Core + Alembic.

```text
backend/
├── alembic/                 # Миграции БД (Alembic)
├── app/
│   ├── core/                # Глобальные настройки (config.py), безопасность (JWT), исключения
│   ├── db/                  # Настройка пула подключений (asyncpg) и глобальный объект MetaData (SQLAlchemy Core)
│   ├── api/                 # Сборка всех роутеров (api_router) из доменов
│   ├── domains/             # Доменные области (бизнес-модули)
│   │   ├── accounts/        # Пример: Счета пользователей
│   │   ├── transactions/    # Пример: Переводы и платежи
│   │   │   ├── router.py      # API endpoints (FastAPI роутеры)
│   │   │   ├── schemas.py     # Pydantic модели (валидация запросов/ответов)
│   │   │   ├── models.py      # SQLAlchemy Core структуры таблиц (Table, Column)
│   │   │   ├── service.py     # БИЗНЕС-ЛОГИКА (проверка баланса, комиссии)
│   │   │   └── repository.py  # Работа с БД (CRUD, сырые/Core SQL-запросы: select, insert)
│   │   └── users/           # Пример: Пользователи и аутентификация
│   └── worker/              # Фоновые задачи (например, Celery/Arq: отправка email, выписки, вебхуки)
├── tests/                   # Интеграционные и юнит-тесты
└── pyproject.toml           # Зависимости и настройки проекта
```

### Ключевые принципы стека и архитектуры:
- **Изоляция доменов:** Каждый модуль в `domains/` автономен. Если одному домену нужны данные из другого (например, `transactions` нужно проверить статус пользователя в `users`), он должен обращаться к нему через его `service.py`, а не лезть напрямую в чужой `models.py` или `repository.py`.
- **SQLAlchemy Core (не ORM):** В `models.py` мы определяем объекты `Table` (структуры таблиц), а не классы моделей ORM. В `repository.py` мы используем функции `select()`, `insert()`, `update()`. Никаких `session.add()`, `relationship()` или ленивой загрузки (lazy loading). Это дает предсказуемость, скорость и полный контроль над SQL.
- **asyncpg:** Используется как высокопроизводительный асинхронный драйвер для работы с PostgreSQL.
- **Слой репозиториев (Repositories):** Вся работа с базой данных инкапсулирована в репозиториях внутри домена. Эндпоинты (API) и сервисы не должны содержать SQL-запросов. Репозитории принимают и возвращают Pydantic-схемы (или словари/Row-объекты, которые мапятся в схемы).
- **Слой сервисов (Services):** Вся бизнес-логика живет здесь. Сервис вызывает репозиторий, проверяет бизнес-правила (например, "достаточно ли средств") и возвращает результат в API.
- **Миграции (Alembic):** Миграции генерируются на основе объектов `Table` из всех файлов `models.py` в доменах. Все изменения схемы БД должны проходить только через Alembic.

## 8. Тестирование (Testing)
- **Изолированная инфраструктура БД:** Всегда используйте `Testcontainers` для автоматического поднятия чистых и изолированных экземпляров PostgreSQL и Redis в Docker при запуске тестов.
- **Транзакционные тесты (Fast):** Для 90% тестов используйте фикстуры, которые оборачивают выполнение теста в SQL-транзакцию (`SAVEPOINT`) с обязательным откатом (`ROLLBACK`) после завершения. Это гарантирует максимальную скорость тестов без необходимости очищать БД вручную.
- **Тесты с реальными коммитами (Real Commits):** Выделяйте в отдельный набор тесты, требующие реального `COMMIT` в базу (например, для проверки `FastAPI BackgroundTasks` или логики вебхуков, срабатывающей после коммита). Для очистки базы в таких тестах используйте `TRUNCATE`.

## 9. Обязательные проверки кода (CI/CD & Linting)
- **Локальный пайплайн:** После любого изменения backend-кода и перед созданием Merge Request (или коммитом) **обязательно** запускайте полный набор проверок:
  ```bash
  make pre-mr-staging-backend
  ```
  Эта команда запустит линтеры, форматтеры, статический анализ типов и проверку безопасности:
  - `ruff` (линтер и автоформаттер)
  - `black` (форматтер кода)
  - `mypy` (строгая статическая типизация)
  - `bandit` (SAST сканер уязвимостей)
  - `pip-audit` (проверка зависимостей на CVE)
- **Исправление ошибок:** Если `make pre-mr-staging-backend` завершается с ошибкой, код не готов. Все предупреждения линтеров и ошибки типов (`mypy`) должны быть исправлены до продолжения работы.

## 10. Обязательный чек-лист после выполнения задачи
Каждый раз после написания кода по задаче разработчик **обязан** пройти следующий чек-лист:
1. **Выполнить `make pre-mr-staging-backend`**: Убедиться, что все линтеры, форматтеры и проверки безопасности проходят без ошибок.
2. **Запустить тесты**: Убедиться, что все тесты (`pytest`) проходят успешно. Написать новые тесты для добавленного функционала.
3. **Проверить зависимости (Deploy)**: Если были изменены, добавлены или удалены зависимости (например, в `pyproject.toml` или `requirements.txt`), это **обязательно** нужно учесть в процессе деплоя (обновить Docker-образы, CI/CD конфигурации и т.д.).
