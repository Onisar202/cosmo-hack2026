# Задача аналитика ВКД

Планировщику нужно ответить на четыре вопроса:

1. Какие внешние воздействия пересекаются с выбранным временем?
2. Чем два окна одинаковой длительности отличаются друг от друга?
3. Какие данные были известны на момент решения?
4. Где вывод надёжен, а где требуется проверка человеком?

**Ценность сервиса:** рекомендация остаётся прослеживаемой до исходных записей и не превращает отсутствие данных в благоприятную обстановку.

<p class="small muted">Прототип поддерживает решение аналитика. Он не выдаёт допуск к реальной ВКД.</p>

<!--

# Что получает пользователь

| Вход                         | Расчёт             | Результат                        |
| ---------------------------- | ------------------ | -------------------------------- |
| режим и время начала         | траектория МКС     | сравнение окон A и B             |
| длительность от 1 до 8 часов | космическая погода | выбранное окно или честный отказ |

# Источники и происхождение данных

| Область             | Источник                | Что фиксируется                                 |
| ------------------- | ----------------------- | ----------------------------------------------- |
| Текущая орбита      | CelesTrak GP/TLE        | оригинал, эпоха, версия, получение              |
| Историческая орбита | NASA ISS TOPO CCSDS OEM | выпуск, EME2000, границы покрытия               |
| Космическая погода  | NOAA SWPC, NASA DONKI   | значение или сообщение, единицы, `published_at` |

Каждая использованная запись получает `record_id`. Манифест результата хранит источник, версию, временные границы и роль записи в расчёте.

# Два независимых механизма

| Космическая погода                            | Метеороидная составляющая MMOD             |
| --------------------------------------------- | ------------------------------------------ |
| GOES и прогнозные продукты NOAA               | годовой продукт NASA MEO для LEO           |
| уведомления NASA DONKI для архивной линии     | `ratio_to_background` вдоль траектории     |
| наблюдение, прогноз и реконструкция разделены | геометрия связывает среду с положением МКС |
| пробел покрытия остаётся пробелом             | нет заявления о вероятности повреждения    |

**Механизмы не складываются в единый балл.** Хорошие данные по одному фактору не компенсируют критический пробел по другому.

<!--
Речь, 30 секунд:
Эксперт подтвердил MMOD как самостоятельный второй механизм. Мы показываем относительное изменение метеороидной среды, но не выдаём его за вероятность попадания или ущерба. Для космической погоды сохраняем различие между измерением, внешним прогнозом и архивным сообщением.

# Прогноз из прошлого без утечки времени

1. `as_of` задаётся не позже начала обоих окон
2. В расчёт входят записи только с `published_at <= as_of`
3. Набор записей и карта покрытия закрепляются в snapshot
4. Поздние наблюдения идут в отдельную проверку результата
5. Неизвестная версия или архивный пробел дают `INSUFFICIENT_DATA`

Историческая траектория выбирается отдельно: NASA OEM должен быть опубликован к `as_of` и покрывать весь расчётный интервал.

<p class="small warn"><strong>Граница готовности:</strong> требование кейса говорит о прогнозе минимум на 6 часов. В реестре исторических линий машиночитаемый горизонт пока не подтверждён, поэтому строгий replay честно исключает непокрытые окна.</p>

<!--
Речь, 35 секунд:

# Правило выбора окна

Окно A выбирается, если оно:

- не хуже B по всем сопоставимым оценкам;
- лучше B хотя бы по одной оценке;
- не содержит критического пробела.

| Ситуация                           | Ответ сервиса          |
| ---------------------------------- | ---------------------- |
| одно окно доминирует               | `selected`             |
| оценки равны                       | `tie`                  |
| механизмы предпочитают разные окна | `insufficient_basis`   |
| данные критично неполны            | `all_windows_excluded` |

`source_agreement` отдельно показывает `CONSISTENT`, `CONFLICT` или `INSUFFICIENT_DATA` между линиями одного механизма.

<!--

# Архитектура и воспроизводимость

```text
Источники данных
      ↓
Нормализация и immutable storage
      ↓
Орбита + оценки Space Weather и MMOD
      ↓
Сравнение окон + warnings + data manifest
      ↓
Один сохранённый result
      ↓
React UI             JSON / HTML export
```

**Стек:** FastAPI, Pydantic, SQLite, SGP4, React, TypeScript, Docker Compose.

Расчётный модуль не читает сеть напрямую. Экспорт не пересчитывает результат.

| Сценарий                    | Проверяемое поведение                      |
| --------------------------- | ------------------------------------------ |
| событие 10–11 мая 2024      | пропуск выраженного события AR3664         |

| Сценарий        | Production                                  | Baseline            | Подтверждённый вывод                        |

# Сценарий демонстрации

1. Открыть публичный URL и показать статус источников
2. Запустить `historical_analysis` для **10 мая 2024, 12:00 UTC**
3. Показать `EVENT_PRESENT`, предупреждение и связанные `record_id`
4. Запустить `historical_forecast` для **11 мая 2024, 00:00 UTC** с `as_of = 11 мая, 00:00 UTC`
5. Показать `INSUFFICIENT_DATA` для незакрытого события вместо «спокойно»
6. Открыть NASA OEM, `source_agreement`, ограничения и coverage
7. Скачать JSON и HTML одного сохранённого result

**Целевое время:** 2,5–3 минуты. Подготовить сохранённый результат на случай сетевого сбоя.

# Что закрыть перед сдачей

1. Исправить Windows-вывод `experiments.run` и сохранить финальные артефакты
2. Обновить эксперимент через актуальный production-путь и получить применимые метрики
3. Зафиксировать доказательство прогнозного горизонта не менее 6 часов
4. Развернуть сервис, выполнить `scripts/smoke.sh` с внешнего устройства
5. Вставить публичный URL и ссылки на сохранённые расчёты
6. Синхронизировать устаревшие разделы `README.md` и `docs/method.md`

**Приоритет:** пункты 1–5 влияют на проверяемость решения жюри. Новые второстепенные функции до сдачи не нужны.
