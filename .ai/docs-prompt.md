# Правила работы с документацией (Docs & Wiki)

Этот документ содержит стандарты ведения документации, структуры Wiki (Confluence) и написания Markdown-файлов в проекте.

**Приоритет при расхождениях:** если какие-либо формулировки здесь противоречат файлу правил [`.cursor/rules/confluence-wiki-format.mdc`](../.cursor/rules/confluence-wiki-format.mdc), **действует версия из `.cursor/rules/confluence-wiki-format.mdc`**. Раздел 7 ниже — копия этих правил для удобства; при расхождении между разделом 7 и файлом `.mdc` снова приоритет у `.mdc`.

## 1. Структура Wiki (Confluence / Внутренняя база знаний)
Документация должна быть структурирована по зонам ответственности, чтобы каждый участник команды (Product, Dev, QA) мог легко найти нужную информацию.

Рекомендуемая структура корневых разделов:
1. **Главная страница (Home):** О проекте, полезные ссылки (прод, тест, Jira, Figma), контакты команды, онбординг.
2. **Процессы и регламенты (How we work):** Общие правила для всей команды. Жизненный цикл задач (workflow), правила работы с Jira, релизная политика, расписание встреч.
3. **Продукт и Аналитика (Product):** Roadmap, бизнес-требования (BRD), эпики, метрики, CJM.
4. **Разработка (Development):** Инструкции по локальному запуску, архитектура, API, Code Style, технический долг.
5. **QA и Тестирование (Testing):** Тестовая стратегия, тест-планы, доступы к стендам.
6. **Инфраструктура и DevOps:** Схемы инфраструктуры, CI/CD, мониторинг (Grafana, Sentry).

## 2. Общие правила написания документации
- **Единый язык:** Вся документация ведется на понятном русском языке (термины можно оставлять на английском: *Merge Request*, *Deploy*, *Issue*).
- **Оглавление (TOC):** В длинных документах обязательно наличие оглавления для быстрой навигации.
- **Нейтральная территория для процессов:** Документы, затрагивающие несколько ролей (например, `process-zadachi.md`, описывающий путь от продакта до релиза), должны лежать в общих разделах ("Процессы и регламенты"), а не прятаться в сугубо технических директориях.
- **Актуальность:** При изменении workflow в Jira или изменении архитектуры, соответствующие таблицы статусов и схемы в документации должны обновляться синхронно.
- **Шаблонизация:** Используйте единые шаблоны для описания фичей (Feature Description) и технических заданий (Tech Design).

## 3. Оформление Markdown
- Используйте четкую иерархию заголовков (`#`, `##`, `###`).
- **Списки:** Обязательно оставляйте пустую строку перед началом списка (маркированного или нумерованного), иначе парсер Confluence может "склеить" его в один абзац.
- **Вложенные списки:** Для создания вложенных списков (подпунктов) в Confluence **обязательно используйте отступ в 4 пробела** (не 2 пробела и не табуляцию), иначе вложенность будет проигнорирована и элементы отобразятся на одном уровне.
- Для таблиц статусов и переходов обязательно указывайте: *Исходный статус*, *Целевой статус*, *Условия перехода* и *Ответственного*.
- Выделяйте важные термины и статусы **жирным шрифтом** или `моноширинным текстом`.
- Ссылайтесь на связанные документы и тикеты в трекере.

## 4. Правила форматирования и использования элементов в Confluence
Для повышения читаемости и удобства навигации в Confluence обязательно использование следующих макросов и элементов оформления:

- **Table of Contents (Оглавление):** Обязательно добавлять макрос TOC в начало любой страницы, которая занимает больше одного экрана.
- **Info / Warning / Note Panels (Панели информации):** 
  - Используйте *Info (синий)* для полезных заметок и ссылок.
  - Используйте *Warning (желтый/красный)* для критичных ограничений, блокеров или устаревшей информации.
  - Используйте *Success (зеленый)* для best practices.
- **Expand (Спойлер / Свертывание):** Прячьте длинные логи, примеры JSON-ответов API, второстепенные детали или объемные куски кода под макрос Expand, чтобы не перегружать страницу.
- **Code Block (Блок кода):** Всегда указывайте язык программирования (Python, Bash, JSON, SQL) для корректной подсветки синтаксиса. Не вставляйте код обычным текстом.
- **Jira Issue / Jira Filter:** Вместо обычных текстовых ссылок на задачи используйте макрос Jira. Это позволяет видеть актуальный статус задачи, исполнителя и эпик прямо на странице Confluence без перехода в трекер.
- **Status (Статус-макрос):** Используйте цветные плашки статусов (например, "В РАБОТЕ", "УСТАРЕЛО", "DRAFT") в начале страницы или в таблицах, чтобы читатель сразу понимал актуальность документа.
- **Упоминания (@mentions):** Если описывается зона ответственности конкретного человека или требуется его ревью, тегайте его через `@Имя`, чтобы ему пришло уведомление.
- **Шаблоны страниц (Page Templates):** Для повторяющихся форматов (Product Requirements, Meeting Notes, Release Notes, Tech Design) используйте стандартизированные шаблоны Confluence, а не создавайте страницы с нуля.

## 5. Автоматизация работы с Confluence (MCP)
**ВАЖНО:** База знаний (Wiki) ведется **исключительно в Confluence**. Не сохраняйте статьи, регламенты и инструкции в виде локальных `.md` файлов в репозитории (в папке `docs/`), чтобы не плодить дубликаты. Всю работу с документацией выполняйте напрямую через Atlassian MCP (`user-Sooperset-Atlassian-MCP`).

**Правила работы через MCP:**
- **Поиск (Search):** Перед созданием новой страницы всегда проверяйте её наличие через `confluence_search` (используя CQL, например: `title ~ "Название"`).
- **Создание (Create):** Генерируйте контент в памяти (или во временном scratchpad) и сразу публикуйте через `confluence_create_page`. Обязательно указывайте Space Key (например, `UojIaLaQSuZr`), формат контента (см. п.6) и `parent_id` для сохранения правильной иерархии (см. п.1). Добавляйте релевантные эмодзи (`emoji`) в заголовок.
- **Обновление (Update):** Для редактирования существующих страниц сначала получите их контент через `confluence_get_page`, внесите изменения и отправьте обратно через `confluence_update_page` по `page_id`.

## 6. Выбор формата контента для Confluence (wiki / markdown / storage)
Этот раздел дополняет раздел 7 и файл `.cursor/rules/confluence-wiki-format.mdc`. **При любом противоречии приоритет у `.cursor/rules/confluence-wiki-format.mdc`.**

MCP-инструменты `confluence_create_page` / `confluence_update_page` принимают три формата: `markdown`, `wiki`, `storage`. **По умолчанию используйте `wiki`** — нативный Confluence wiki-markup, его парсер устойчив к многострочным code-блокам и корректно рендерит макросы.

**Когда какой формат:**
- **`wiki` (по умолчанию для большинства страниц):** Для страниц с code-блоками, многострочными shell/bash-командами (особенно с `\` переносами), макросами Info/Warning/Note, TOC, таблицами. Markdown-парсер Confluence иногда "теряет" одиночные code-fences (``` ```) и однострочные code-блоки рендерятся обычным текстом — wiki этого лишён.
- **`markdown`:** Только для простых страниц без код-блоков и макросов (например, короткая заметка, ссылочная страница, changelog).
- **`storage`:** Когда нужен максимальный контроль (нестандартные макросы, точное форматирование). Используйте только если wiki не справляется.

**Шпаргалка по wiki-разметке (обязательно к использованию):**

| Элемент | Wiki-синтаксис |
|---|---|
| Заголовки | `h1.`, `h2.`, `h3.` (после точки — пробел и текст) |
| Code-блок с подсветкой | `{code:bash}` ... `{code}` (укажите язык: `bash`, `python`, `json`, `sql`, `yaml`) |
| Code-блок без языка | `{code}` ... `{code}` |
| Info-панель (синяя) | `{info:title=...}` ... `{info}` |
| Warning-панель (жёлтая/красная) | `{warning:title=...}` ... `{warning}` |
| Note-панель (серая) | `{note}` ... `{note}` |
| Tip-панель (зелёная) | `{tip}` ... `{tip}` |
| TOC | `{toc:minLevel=2\|maxLevel=3}` |
| Expand (спойлер) | `{expand:Заголовок}` ... `{expand}` |
| Таблица (header + cell) | `\|\|h1\|\|h2\|\|` на строке заголовков, `\|c1\|c2\|` на строках данных |
| Жирный / курсив / моно | `*bold*`, `_italic_`, `{{monospace}}` |
| Ссылка | `[текст\|https://url]` или `[текст\|SPACE:Page Title]` |
| Нумерованный список | `#` в начале строки (вложенный — `##`) |
| Маркированный список | `*` в начале строки (вложенный — `**`) |
| Галочка / чек | `(/)` (зелёная), `(x)` (красная), `(!)` (жёлтая) |

**Типичные ошибки, которые ломают рендер в markdown и не ломают в wiki:**
- Одиночная строка в ```bash ... ``` — markdown-парсер Confluence может отрендерить её как inline-текст, wiki `{code:bash}` всегда корректно.
- Многострочная команда с `\` переносами — в markdown может распасться на несколько фрагментов, в wiki остаётся цельным блоком.
- Эмодзи ✅ / ⚠️ в начале строки внутри code-блока — markdown может интерпретировать как status-плашку. В wiki внутри `{code}` всё остаётся сырым текстом.

**Пример правильного вызова `confluence_update_page`:**
```
content_format: "wiki"
content: |
  h2. Оглавление
  {toc}

  h2. Пример
  {code:bash}
  export BRAND=test
  source scripts/e2e_env.sh
  {code}

  {info:title=Подсказка}
  Для production используйте только readonly-smoke.
  {info}
```

**Проверка после публикации:** Откройте страницу в браузере и убедитесь, что:
1. Все code-блоки имеют тёмный фон и подсветку синтаксиса.
2. Info/Warning панели видны цветными прямоугольниками (а не как `>` blockquote).
3. TOC сгенерирован и кликабелен.
4. Таблицы выровнены, заголовки выделены жирным.
Если что-то из этого не так — переключите `content_format` на `wiki` или `storage` и перепубликуйте.

## 7. Confluence: всегда wiki-формат (копия `.cursor/rules/confluence-wiki-format.mdc`)

*Ниже — текст правила из репозитория. При расхождении с любым другим разделом этого файла приоритет у актуальной версии [`.cursor/rules/confluence-wiki-format.mdc`](../.cursor/rules/confluence-wiki-format.mdc).*

При вызовах `confluence_create_page` / `confluence_update_page` (MCP `user-Sooperset-Atlassian-MCP`) **по умолчанию используй `content_format: "wiki"`**, не `markdown`.

Причина: markdown-парсер Confluence теряет одиночные code-fences, ломает многострочные shell-команды с `\` и непредсказуемо интерпретирует эмодзи (✅, ⚠️) в начале строк внутри code-блоков. Wiki-markup — нативный формат Confluence, все макросы гарантированно работают.

### Когда markdown всё же OK

- Простая текстовая заметка без code-блоков и макросов.
- Changelog / короткая ссылочная страница.

Для всего остального (runbook, tech-design, API-доки, инструкции) — **wiki**.

### Шпаргалка по wiki-синтаксису

| Элемент | Синтаксис |
|---|---|
| Заголовки | `h1.` / `h2.` / `h3.` (точка + пробел) |
| Code с подсветкой | `{code:bash}` ... `{code}` (языки: `bash`, `python`, `json`, `sql`, `yaml`) |
| Info (синяя) | `{info:title=...}` ... `{info}` |
| Warning (жёлтая/красная) | `{warning:title=...}` ... `{warning}` |
| Note (серая) | `{note}` ... `{note}` |
| Tip (зелёная) | `{tip}` ... `{tip}` |
| TOC | `{toc:minLevel=2\|maxLevel=3}` |
| Expand (спойлер) | `{expand:Заголовок}` ... `{expand}` |
| Таблица | `\|\|h\|\|h\|\|` (заголовок), `\|c\|c\|` (строка) |
| Моноширинный | `{{text}}` |
| Ссылка | `[текст\|url]` |
| Чек в списке | `(/)` (зелёный), `(x)` (красный), `(!)` (жёлтый) |

### Пример

```
h2. Быстрый старт

{toc}

{info:title=Подсказка}
Для production используйте только readonly-smoke.
{info}

{code:bash}
export BRAND=test
source scripts/e2e_env.sh
{code}

||Параметр||Значение||
|{{BRAND}}|{{test}}|
|{{BRAND_DOMAIN}}|{{test.example.com}}|
```

### Проверка после публикации

Открой страницу в браузере и убедись:
1. Code-блоки имеют тёмный фон и подсветку языка.
2. Info/Warning-панели — цветные прямоугольники, а не текстовые blockquote.
3. TOC сгенерирован и кликабелен.

Если что-то выглядит как обычный текст (особенно однострочные команды) — переключи `content_format` на `wiki` и перепубликуй.
