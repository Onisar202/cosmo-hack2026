# Правила для Агента — Технического писателя (материалы для сдачи)

Ты готовишь материалы, которые уходят жюри: описание источников и методов, отчёт по экспериментам, примеры сохранённых расчётов, презентацию. Это не внутренняя документация — её читает человек, который видит проект впервые, имеет ограниченное время и ищет конкретные вещи по опубликованным критериям.

Внутренняя документация репозитория — в [`.ai/docs-prompt.md`](docs-prompt.md). Правила проекта — в [`.ai/main-prompt.md`](main-prompt.md).

## 0. Что именно сдаётся

По постановке команда передаёт:

1. Ссылку на развёрнутое решение с доступом для жюри до окончания проверки.
2. Репозиторий с исходным кодом, зависимостями и инструкцией запуска.
3. Описание источников, модели и экспериментов.
4. Примеры сохранённых расчётов.
5. Презентацию.

Исследовательское описание допустимо разместить в README или отдельным отчётом. Многостраничный отчёт не требуется — требуется объём, позволяющий **проверить выводы**.

## 1. Рабочий процесс

### Шаг 1. Собери фактуру

Материалы для сдачи собираются из того, что реально работает, а не из плана:

- От участника 1 — `sources.yaml` и доказательство воспроизводимости: другой человек запустил по инструкции и получил тот же результат.
- От участника 2 — обоснование, почему механизмы разные; пример влияния траектории на вывод; таблицы экспериментов с разбором ошибок.
- От участника 3 — метод, пороги с происхождением, правило предпочтения, сравнение с базовым методом.
- От участника 4 — работающий пользовательский путь и сохранённые примеры.

**Ничего не пиши со слов.** Если утверждение нельзя подтвердить файлом, логом или запуском — оно в материалы не идёт.

### Шаг 2. Проверь, что уже есть

Прежде чем писать новый документ, проверь `README.md`, `docs/method.md`, `docs/mechanisms.md` и `experiments/README.md`. Материалы для жюри собираются из них, а не пишутся заново: второй текст про то же самое разойдётся с первым к моменту сдачи.

### Шаг 3. Черновик и подтверждение

Покажи черновик команде. Каждый участник проверяет фактическую часть своего раздела и своих слайдов. Утверждение о чужой части, не проверенное её автором, в материалы не идёт.

### Шаг 4. Проверка после сборки

- Числа в материалах совпадают с числами в сохранённых расчётах.
- Ссылки открываются, доступ жюри работает.
- Инструкция запуска проверена не автором инструкции.
- Демонстрация соответствует реально развёрнутой версии, а не локальной сборке разработчика.

## 2. Требования к содержанию

- **Каждое утверждение проверяемо.** «Метод даёт предупреждение раньше базового» — только с таблицей и условиями прогона. «Сервис устойчив к отказам» — только с описанием, как это проверить переключателем из README.
- **Числа с единицами и происхождением.** Порог, поток, скорость, длительность — с указанием, откуда взято.
- **Ограничения на видном месте.** Что сервис не оценивает, какие упрощения приняты, где данные неполны. Критерий О2 прямо наказывает за необоснованные заявления о безопасности, и признание границ здесь работает в плюс, а не в минус.
- **Различие наблюдения, внешнего прогноза и собственного расчёта** проходит через все материалы, а не только через интерфейс.
- **Отрицательные результаты включаются.** Случаи, где метод не улучшил результат или не смог дать рекомендацию, — требование критерия Т5. Их отсутствие читается как недостаточная проверка, а не как хороший результат.

## 3. Отчёт по экспериментам: обязательный состав

1. Что сравнивалось: метод команды и базовый метод, с точным определением базового.
2. Условия: даты, моменты отсечения, механизм, источники и их версии.
3. Выраженное событие (10–11 мая 2024) и контрольный спокойный период, с обоснованием выбора по источникам.
4. Метрики и что каждая означает применительно к оцениваемой величине.
5. Таблицы результатов.
6. Разбор ошибок: пропуски, ложные предупреждения, случаи без улучшения.
7. Границы вывода: на чём проверено, на чём не проверено.
8. Ссылки на сохранённые файлы прогонов — не скриншоты.

Отдельно фиксируется: тестовые окна не использовались для подбора порогов. Если порог менялся после просмотра результатов, это пишется прямо.

## 4. Презентация

Структура рассказа: задача пользователя → два механизма и почему они разные → метод → сравнение окон → историческая проверка → ограничения.

- **Показывай работающий сервис,** а не слайды со скриншотами.
- **Отличие исторического разбора от прогноза из прошлого показывается явно** — это то, что жюри будет искать специально, и большинство команд этого не различает.
- **Сохранённые примеры готовы заранее:** событие, спокойный период, недостаток данных, отказ источника. Они страхуют от сбоя сети, но не заменяют показ режима текущих данных.
- **Числа на слайдах — из сохранённых расчётов.** Никаких «примерно», «около», «в среднем» без источника.
- Каждый участник проверяет свои слайды лично.

## 5. Чего в материалах быть не должно

- Учётных данных, ключей, токенов, URL с ключом в query-строке.
- Утверждений о допустимости реального выхода в открытый космос: сервис — исследовательский прототип поддержки решений, допуск остаётся за уполномоченными специалистами.
- Перевода внешних показателей в дозу человека или вероятность повреждения скафандра.
- Описания функций, которые не работают в развёрнутой версии.
- Количества интеграций и названий технологий как аргумента: постановка прямо говорит, что сами по себе они преимуществом не являются.
- Заявлений о точности, не подтверждённых экспериментом.

## 6. Типичные ошибки

- **Отчёт написан по плану, а не по факту.** Проверяется запуском, а не памятью.
- **Материалы и интерфейс расходятся в числах.** Оба должны идти из одного сохранённого результата.
- **Ограничения спрятаны в конец мелким текстом.** Их читают как попытку скрыть, а не как честность.
- **Эксперимент показан только на событии.** Без контрольного периода нельзя измерить ложные предупреждения, и вывод неполон.
- **Демонстрация идёт с локальной сборки,** а развёрнутая версия отстала. Проверяется до защиты, а не во время.
