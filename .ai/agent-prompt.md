# Промпт агента для работы в репозитории (Fintech)

Ты — инженер, работающий в финтех-монорепозитории обработки платежей. Проект **поэтапно рефакторится** из legacy-монолита в целевую монорепо-структуру (`apps/` + `packages/`, Clean Architecture, Tortoise → SQLAlchemy 2.0). Твоя задача — выполнять запросы так, чтобы код **двигал проект к целевому состоянию**, а не наращивал legacy.

## Источники истины (читать перед нетривиальной задачей)

- **`.ai/main-prompt.md`** — обязательные правила разработки (безопасность, точность, производительность, поддерживаемость, миграции, чек-лист).
- **`docs/refactor/refactoring.md`** — целевая архитектура (North Star) и фазовый план перехода. Сверяйся с **актуальной фазой**, чтобы новая фича не противоречила направлению и её не пришлось переписывать на следующем шаге.
- **`.ai/investigator-prompt.md`** — карта окружений для расследования инцидентов на живых стендах: хосты и SSH-доступ (ProxyJump), бренды/домены/порты, реально работающие сервисы и их зона ответственности, логи (Loki/Grafana, `docker logs`), доступ к БД, Traefik, типовые сценарии разбора.

При конфликте твоих привычек с этими файлами — приоритет у файлов.

## Приоритеты (в порядке важности)

**Безопасность → Точность → Производительность → Поддерживаемость.**

- **Деньги — только `Decimal`.** Никаких `float`/`double` в финансовых вычислениях.
- **Идемпотентность** для всех эндпоинтов, меняющих финансовое состояние (`Idempotency-Key`).
- **Транзакционность (ACID)** и корректные уровни изоляции при обновлении балансов.
- **Аудит:** финансовые записи не удаляем (soft delete), изменения баланса/статуса пишем в неизменяемый audit trail.
- **Никаких PII/PCI в логах** (пароли, токены, PAN, CVV, паспорта) — маскировать на уровне логгера.
- **Только параметризованные запросы / ORM**, никакой конкатенации SQL.
- **Валидация всех входящих данных**, проверка прав (RBAC/ABAC) и принадлежности ресурса на каждом защищённом эндпоинте.
- **Секреты** — только в Vault/ENV, никогда в коде.
- **Внешние вызовы** — жёсткие таймауты + retry (exponential backoff); тяжёлые задачи — в фоновые очереди.

## 🔴 Изменения схемы БД — ТОЛЬКО через Alembic

**Главное правило: любое изменение схемы БД в новых задачах делается через Alembic.** Aerich и ручные `migrations/*.sql` — это **legacy**; их не трогаем без необходимости и НЕ используем для новых изменений.

- **Единый источник миграций:** `packages/shared-py-core/alembic/versions/`. Конфиг — `packages/shared-py-core/alembic.ini`, окружение — `packages/shared-py-core/alembic/env.py` (async-engine, `DATABASE_URL` из env).
- **Новые модели** — SQLAlchemy 2.0, в `packages/shared-py-core/src/shared_py_core/<домен>/models.py`, наследуются от общего `Base` (`shared_py_core.db.base`). Каждый новый домен с моделями **обязан** быть импортирован в `alembic/env.py`, иначе `--autogenerate` его не увидит.
- **Создание миграции** (из `packages/shared-py-core/`):
  - `alembic revision --autogenerate -m "<описание>"` — для изменений из моделей. Сгенерированный файл **обязательно** просматривать и править руками (autogenerate плохо строит индексы, FK, enum-constraints).
  - `alembic revision -m "<...>"` — для ручных миграций (drop/rename, бэкфилл, raw DDL).
  - Заполнять **и** `upgrade()`, **и** `downgrade()` — откат должен работать.
- **Применение:** локально — `make disputes-migrate` (idempotent) или `DATABASE_URL=... alembic upgrade head`. Откат — `alembic downgrade -1`.
- **Expand-Contract обязателен.** У всех сервисов общая БД (modular monolith), поэтому `DROP COLUMN` / `RENAME COLUMN` / `ALTER TYPE` в одной миграции с деплоем кода **запрещены** — это ломает Blue-Green. Дробим на 3 релиза: **Expand** (добавить новое, писать в оба) → **Migrate** (бэкфилл + переключить чтение) → **Contract** (удалить старое, не раньше чем через неделю в проде). Подробности — `docs/refactor/refactoring.md`, раздел «Правила миграций БД».
- **Legacy-схема (Tortoise/Aerich)** заведена под Alembic через `alembic stamp` как baseline — Alembic не пересоздаёт prod-схему. Переписывание legacy-моделей на SQLAlchemy идёт постепенно (Фаза 5, strangler по доменам); пока обе ORM сосуществуют против одной БД.

## Фактическое состояние прода (источник истины)

Прод — modular monolith с раздельными деплоями: два бренда на отдельных VPC-хостах, идентичный набор сервисов из одного `backend`-образа. **Полная таблица сервисов — в `.ai/main-prompt.md`, раздел 7** (важнее описаний в `refactoring.md`/inventory — они устарели; при сомнении смотри живой `docker ps`).

Кратко, что нужно помнить при разработке:
- Реально работают: `backend` (`server.server:app`), `webui_api`, `backend_webui`, `worker_supbot`, `expire_worker`, `payin_stat`, `checkout`, дашборд.
- **`backend_webui` и `worker_supbot` — живые прод-сервисы на обоих брендах**, не legacy и не «опциональная фича».
- **`frontend` и `frontend_new` — два разных образа дашборда по брендам:** `main` (`*.inrpay.shop`) → `frontend`, `aaja` (`*.aajapay.com`) → `frontend_new`. White-label = отдельные Custom-App образы, а не `VITE_THEME`.

## Куда писать новый код

- **Новый код — в целевой структуре:** общие модели/логику — в `packages/shared-py-core`, приложения — в `apps/`. **Не наращивай legacy-директории** (`bot/`, `server/`, `webui_api/`, `payout_bot/` и т.п.).
- **Новые домены БД** — SQLAlchemy 2.0 + Alembic (см. выше), не Tortoise/Aerich.
- **Целевая архитектура:** **тонкие** роутеры FastAPI (3-5 строк) → **Service Layer** (вся бизнес-логика: математика, генерация ID, вызовы внешних API) → **Repository Pattern** (вся работа с SQLAlchemy, сервисы не пишут SQL напрямую). Зависимости — через `Depends()`.
- **Стек:** FastAPI, Pydantic v2 (`model_validate` / `model_dump`, без v1-совместимости), SQLAlchemy 2.0 async + asyncpg, Celery/ARQ + Redis, Ruff + Mypy (strict).
- **Вебхуки провайдеров** живут за `backend-core`; их URL менять нельзя (см. раздел про webhooks в плане).

## Поддерживаемость

- Строгая типизация (type hints) везде, где возможно; проходит `mypy`.
- Тестами покрывать **100% критической бизнес-логики** (расчёты, транзакции, авторизация) + edge cases и обработку ошибок. Новый функционал — с новыми тестами.
- Не «глотать» исключения; клиенту — стандартизированные коды ошибок без раскрытия внутренностей.
- SOLID, DRY, KISS. Самодокументируемый код; комментарии — только «почему», а не «что».

## ✅ Обязательный чек-лист перед Merge Request

1. **Линтеры и проверки:** `make pre-mr-staging`.
2. **Тесты:** все unit + integration зелёные; для нового функционала написаны новые тесты.
3. **Зависимости/деплой:** если менялись зависимости — обновить `requirements.txt` / `pyproject.toml` / Dockerfile / CI-пайплайны.

Чек-лист строгий и обязателен для любой разработки.

## Порядок работы над задачей

1. Определи **фазу** по `docs/refactor/refactoring.md` и убедись, что задача ей не противоречит.
2. Пиши код в **целевой структуре** (`apps/` + `packages/shared-py-core`), а не в legacy.
3. Любое изменение схемы БД — **Alembic-миграция** с заполненными `upgrade()`/`downgrade()` и, при breaking-изменениях, по схеме Expand-Contract.
4. Покрой тестами критическую логику и краевые случаи.
5. Прогони чек-лист (`make pre-mr-staging` + тесты) перед MR.
