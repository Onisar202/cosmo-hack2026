# Правила расследования проблем (Investigator)

Этот документ — рабочая карта для агента, который **разбирается, почему сервис ведёт себя не так**: «источник не отвечает», «в архиве пробел», «выгрузка не совпадает с интерфейсом», «результат не воспроизводится», «подозрение, что в прогноз попали поздние данные», «рекомендация не объясняется данными».

Читается вместе с [`.ai/main-prompt.md`](main-prompt.md) (§1 временная честность, §2 данные и пропуски — источник истины о том, как обязано себя вести).

---

## 0. Принципы разбора

1. **Read-only по умолчанию.** Разбор не чинит. Никаких правок данных, очистки кеша, перезапуска сервиса, пересохранения результата — до явного разрешения человека. Очистка кеша уничтожает ровно то состояние, которое нужно для доказательства.
2. **Сначала факты, потом гипотезы.** Каждое утверждение опирается на конкретный вывод: строку лога, поле записи, ответ API. Формулировку «скорее всего», не подкреплённую выводом, помечай как гипотезу явно.
3. **Фиксируй время и часовой пояс.** Всё внутри — UTC. Пользователь называет время в местном. Всегда переводи и пиши в отчёте UTC-окно.
4. **Идентификаторы — якорь разбора.** Тянись за `result_id`, `record_id`, `source_id`, `as_of`, эпохой орбитальных элементов. Один `result_id` связывает все этапы расчёта в логах.
5. **Определи режим первым делом.** `current`, `historical_analysis` и `historical_forecast` — три разных пути кода с разными правилами отбора данных. Разбор не в том режиме — потерянное время.
6. **Отличай «неверно» от «ожидаемо неприятно».** Отсутствие рекомендации, равнозначные окна и «оценить невозможно» — это корректные состояния по постановке, а не баги. Прежде чем чинить, проверь, не является ли наблюдаемое требуемым поведением.
7. **Секреты не покидают окружение.** В отчёт не попадают учётные данные Space-Track, ключи API и URL с ключом в query-строке. Только имена переменных.

## 1. Что смотреть в первую очередь

| Симптом | Первая проверка |
| --- | --- |
| Пустой или странный результат | Режим запроса и `as_of`; затем статусы источников на момент расчёта |
| Источник «не работает» | Код ответа и длительность в логе обращения; квота и `429` отдельно от сетевых ошибок |
| Пробел в данных | Реальный охват архива по `sources.yaml` против запрошенного интервала |
| Выгрузка ≠ интерфейс | Читают ли оба один `result_id`, или отчёт собирается заново |
| Результат не воспроизводится | Совпадают ли `algorithm_version` и `data_manifest`; не читает ли расчёт текущее время внутри |
| Подозрение на утечку времени | `published_at` каждой записи из манифеста против `as_of` |
| Рекомендация не объясняется | Какой шаг правила предпочтения сработал; ссылки на `record_id` в предупреждениях |
| Геометрия выглядит неверной | Эпоха элементов, их давность, признак реконструкции, система координат |

## 2. Разбор подозрения на утечку времени

Самый дорогой класс проблем в проекте и первый, который будет проверять жюри.

1. Возьми `result_id` и достань `data_manifest`.
2. Для каждой записи манифеста сравни `published_at` с `as_of` результата. Любая запись с публикацией позже отсечения — подтверждённая утечка.
3. Проверь `replay_eligible` каждой записи: попадание записи с ложным флагом — тоже утечка, даже если публикация была раньше.
4. Проверь косвенные пути: агрегаты, посчитанные по всему архиву; «последнее известное значение», взятое без фильтра; справочники и календари, собранные после `as_of`; кеш, заполненный запросом в режиме `current`.
5. Проверь, не читает ли расчётная функция текущее время внутри себя вместо аргумента.
6. Воспроизведи: добавь в хранилище запись с публикацией позже `as_of` и повтори расчёт. Изменение любого поля результата — доказательство.

Отсутствие изменения не доказывает отсутствие утечки по другим путям — проверь пункты 2–5 отдельно.

## 3. Разбор отказа источника

1. Найди в логах обращения к источнику за интервал: код ответа, длительность, размер, попадание в кеш.
2. Отличи классы: таймаут, отказ соединения, `429` по квоте, `4xx` по правам или параметрам, `200` с пустым или изменившимся телом.
3. **Проверь главное:** что сервис показал пользователю. Отказ обязан дать статус «оценить невозможно» либо кеш с явной давностью. Если на экране оказалась благоприятная оценка — это блокировщик уровня §2, а не проблема источника.
4. Проверь, не упал ли из-за одного источника весь расчёт: отказ одного продукта должен давать неполноту по своему фактору, а не пустой результат.
5. Проверь, сохранилась ли давность в кеше.

## 4. Разбор расхождения выгрузки и интерфейса

1. Сравни `result_id` в обоих.
2. Если идентификаторы разные — интерфейс показывает один расчёт, выгрузка собирает другой. Это нарушение §3 main-prompt, чинится не сверкой полей, а тем, что оба читают один сохранённый объект.
3. Если идентификатор один, а поля разные — ищи преобразование на стороне отображения: округление, форматирование времени по локальной таймзоне, подстановку значения вместо `null`.

## 5. Что запрещено при разборе

- Править сохранённые результаты и записи источников.
- Чистить кеш «чтобы проверить гипотезу» до того, как состояние зафиксировано.
- Перезапускать сервис до снятия логов.
- Подменять источник статическим файлом и объявлять проблему невоспроизводимой.
- Выводить в отчёт учётные данные и ключи.

Всё это — отдельным шагом «починка» по явному решению, а не частью разбора.

## 6. Формат отчёта

```markdown
## Симптом
Что наблюдал пользователь, когда (UTC), в каком режиме, с какими параметрами запроса.

## Затронутая область
Режим, result_id, источники, идентификаторы записей, слой кода.

## Хронология (UTC)
14:02:11 — запрос historical_forecast, as_of 2024-05-10T12:00:00Z (лог, result_id 8f3c…)
14:02:12 — выборка вернула запись DONKI с published_at 2024-05-10T18:41:00Z (запись store, record_id …)

## Корневая причина
Однозначно, с доказательством. Если не доказана — «Наиболее вероятная причина» и что нужно для подтверждения.

## Масштаб
На какие режимы, даты и механизмы это влияет. Затронуты ли уже сохранённые результаты и материалы экспериментов.

## Что НЕ является причиной
Проверенные и отвергнутые гипотезы — экономит время следующему.

## Рекомендации
- Немедленно: …
- Постоянное исправление: … (файл и слой)
- Тест, которого не хватило: … (какой из восьми обязательных по §9 поймал бы это)

## Воспроизведение
Точные команды и параметры запроса.
```

Короткая выжимка в 2–5 строк идёт в общий чат команды, полный разбор — в файл в репозитории. Разбор, оставшийся только в переписке, через день считается несделанным: никто не помнит, какие гипотезы уже отвергли.

## 7. После починки

Каждый подтверждённый дефект временной честности, обработки пропусков или отказов **обязан** получить тест, который его ловит. Если такого теста нет в наборе из §9 main-prompt — добавь его туда, а не только в файл своего модуля.
