# Правила разработки Backend (сервис прогнозирования рисков ВКД)

Этот документ описывает инженерные стандарты backend-части. Цена ошибки здесь — не деньги, а **правдоподобный неверный вывод**: сервис, который уверенно рекомендует окно на основании данных, которых у него не было, выглядит работающим и проходит поверхностную проверку. Поэтому базовая установка — паранойя относительно времени, происхождения и полноты данных.

Читается вместе с [`.ai/main-prompt.md`](main-prompt.md). Предметные решения кейса — §11 main-prompt, требования и критерии — §12.

## 1. Ядро: запись источника и результат расчёта

Аналог ledger в этом проекте — **неизменяемая запись источника** и **неизменяемый результат расчёта**. Обе сущности append-only.

- **Запись источника не обновляется и не удаляется.** Поздняя версия того же продукта — это новая запись со своим `published_at` и `source_version`, лежащая рядом с прежней. Перезапись версии уничтожает возможность строгого replay, и восстановить её потом нечем.
- **Обязательные поля записи** (схема — в `contracts/`): `record_id`, `source_id`, `source_url`, `record_kind` (наблюдение / прогноз / предупреждение / орбитальные элементы), `observed_at`, `valid_from`, `valid_to`, `published_at`, `fetched_at`, `value`, `unit`, `spatial_context`, `source_version`, `raw_ref`, `checksum`, `quality`, `replay_eligible`. Для орбитальных данных дополнительно — эпоха элементов, формат и система координат. Ни одно из четырёх времён (`observed_at`, `valid_from`/`valid_to`, `published_at`, `fetched_at`) не заполняется значением другого «потому что так удобнее».
- **`replay_eligible` вычисляется при записи, а не при чтении.** Если время публикации или версия неизвестны, флаг ложный и запись навсегда непригодна для строгого прогноза из прошлого. Восстановить флаг задним числом по дате измерения нельзя — это и есть подделка replay.
- **Результат расчёта неизменяем.** Пересчёт создаёт новый `result_id`. Нет эндпоинта, который правит существующий результат.
- **Каждый результат несёт `algorithm_version` и `data_manifest`** — список конкретных `record_id` с версиями. Манифест собирается фактически использованными записями, а не повторным запросом к хранилищу «примерно за тот же период».
- **Режим — часть результата.** По сохранённому объекту всегда видно, был это текущий запрос, исторический разбор или прогноз из прошлого, и каким было `as_of`.

## 2. Хранение и конкурентность

- **Разделяй горячее и холодное:** оригиналы ответов (файлы или BLOB с контрольной суммой) и нормализованные записи (таблица с индексами по `source_id`, `published_at`, `observed_at`).
- **Индексы под реальные запросы:** выборка «все записи продукта X с `published_at <= as_of`, наибольшая версия на каждый интервал» — основной запрос строгого replay, он должен быть быстрым и покрытым тестом.
- **Одновременные запросы изолированы.** Параметры, статусы и результаты разных расчётов не смешиваются. Никакого состояния расчёта в модульных переменных: контекст передаётся явно.
- **Никаких жёстких удалений** записей источников и результатов. Очистка кеша — отдельная операция, не затрагивающая сохранённые расчёты.
- **Перезапуск не уничтожает сохранённые расчёты.** SQLite-файл и каталог оригиналов лежат в томе, а не во временной директории контейнера.

## 3. Внешние источники данных

Источники — NOAA SWPC, архив NOAA NCEI, NASA CCMC DONKI, CelesTrak, Space-Track. Они падают, меняют формат, отдают пустой ответ с кодом 200 и имеют квоты.

- **Жёсткие таймауты на соединение и чтение для каждого вызова.** Вызов без таймаута — блокировщик на ревью.
- **Ограниченные повторы с экспоненциальной задержкой** для временных ошибок. Повтор по `429` — только после паузы, продиктованной квотой, и с ограничением общего числа попыток.
- **Ответ валидируется по схеме до записи.** Код 200 с пустым или неожиданным телом — это ошибка источника, а не набор нулей.
- **Парсер пишется под сохранённый реальный ответ.** В репозитории лежат примеры ответов каждого источника; тест парсера гоняется на них.
- **Изменение формата источника обнаруживается тестом, а не пользователем.** Схема ответа проверяется явно, неизвестные поля не роняют парсер, но и не игнорируются молча в критичных местах.
- **Статус источника — отдельная сущность:** время последнего успешного получения, время последней ошибки, текст ошибки, действует ли заморозка. Отдаётся API рядом со значениями, а не вместо них.
- **Переключатель отключения и заморозки источника** реализуется на уровне слоя `sources/`, работает без перезапуска и документирован в README.

## 4. Секреты, лицензии и условия использования

- **Учётные данные Space-Track и ключи API — только из переменных окружения.** В репозитории `.env.example` с именами и комментариями.
- **Никаких секретов в логах**, включая полные URL с ключом в query-строке. Маскирование на уровне логгера.
- **Условия использования источника соблюдаются:** частота запросов, разрешённость локального кеша, требования к атрибуции. Ограничения записываются в `sources.yaml` рядом с продуктом.
- **Коммерческие данные не должны быть необходимы** для работы сервиса. Если источник требует платного доступа, он может быть только дополнением, и сервис обязан работать без него.

## 5. Наблюдаемость

- **`result_id` — сквозной идентификатор.** Он прокидывается в логи всех этапов расчёта: выборка данных, геометрия, оценка механизмов, сравнение окон. По одному идентификатору должна восстанавливаться вся история конкретного расчёта.
- **Структурированное логирование** в stdout, по одной записи на строку. Обязательные поля: `result_id`, `mode`, `as_of`, этап, `source_id` при обращении к источнику.
- **Логируется каждое обращение к источнику:** URL без секретов, код ответа, длительность, размер, попал ли ответ в кеш.
- **Логируется решение о пригодности записи** для строгого replay с причиной отказа. Это первое, что смотрят при разборе подозрения на утечку времени.
- **Не глотать исключения.** Ошибка источника превращается в статус источника, а не в пустой список записей.

## 6. API и валидация

- **Строгая схема запроса (Pydantic):** режим, UTC-времена, `duration_hours` в диапазоне 1–8, период поиска до 24 часов, согласованность интервалов, обязательность `as_of` для `historical_forecast`, запрет `as_of` для `current`.
- **Валидация исторического диапазона:** дата внутри 1 мая — 30 июня 2024 принимается, за его пределами — понятная ошибка с указанием поддерживаемого периода, а не пустой результат.
- **Расчётный интервал шире периода поиска.** Сервер сам считает верхнюю границу как `search_end_at + duration`, до 32 часов. Это не обязанность клиента.
- **Стандартизированный формат ошибок** с кодом и понятным сообщением. Никаких трассировок в ответе.
- **Операции:** запуск расчёта, статус задачи, получение результата, список сохранённых, принудительное обновление источников, статусы источников.
- **Статус длительной операции — реестр задач в процессе.** Брокер очередей здесь избыточен: считает сервис быстро, ждёт только сеть.
- **Ответ всегда содержит полноту и ограничения**, даже когда расчёт успешен. Успешный ответ без блока `coverage` и `limitations` считается неполным контрактом.

## 7. Архитектура и структура

Структура каталогов — в `.ai/main-prompt.md`, §8. Ключевые принципы:

- **Слои:** `sources/` (получение и нормализация) → `store/` (хранение, версии, выборка по `as_of`) → `domain/` (расчёты) → `api/` (тонкие роутеры) → `export/` (выгрузка).
- **`domain/` — чистые функции.** Принимают записи и параметры, возвращают оценки. Ни сети, ни обращений к хранилищу, ни чтения времени «сейчас» внутри расчёта: текущий момент передаётся аргументом. Иначе исторический режим невоспроизводим и нетестируем.
- **Изоляция механизмов:** `spaceweather/`, `mmod/`, `orbit/`, `lighting/` не импортируют друг друга напрямую. Общее — это результат геометрии из `orbit/`, который передаётся явно.
- **`windows/` объединяет оценки механизмов** и реализует правило предпочтения из §11 main-prompt. Правило — одна функция, покрытая тестами на все состояния: победитель, равенство, отсутствие улучшения, невозможность оценки.
- **Зависимости через `Depends()`**, конфигурация — объект настроек, а не чтение `os.environ` по коду.
- **Стек:** Python 3.11+, FastAPI, Pydantic v2, SGP4/Skyfield, SQLite, httpx с явными таймаутами.

## 8. Тестирование

- **Обязательный минимум — восемь тестов из `.ai/main-prompt.md`, §9.** Это не рекомендация: каждый из них закрывает конкретный способ получить правдоподобный неверный результат.
- **Расчётные модули тестируются на зафиксированных входах,** а не на живых источниках. Живая сеть в тестах делает их недетерминированными.
- **Коннекторы тестируются на сохранённых реальных ответах** из репозитория.
- **Тест на утечку времени пишется первым,** до реализации исторического режима. Написанный после — почти всегда подтверждает уже сделанную реализацию вместо того, чтобы её проверять.
- **Численная часть проверяется независимым примером.** Для орбиты — другая библиотека или опубликованная эфемерида; для геометрии тени и радианта — вычисленный вручную случай с известным ответом.

## 9. Обязательные проверки перед передачей кода

1. Линтер и форматтер без ошибок.
2. Проверка типов без ошибок.
3. Все тесты зелёные, для нового функционала написаны новые.
4. Нет сетевых вызовов без таймаута.
5. Нет `datetime` без таймзоны.
6. Нет секретов в коде и логах.

## 10. Обязательный чек-лист после выполнения задачи

1. Прогнать проверки из §9.
2. Если менялся контракт — обновить `contracts/` и все четыре фикстуры, уведомить участников 3 и 4.
3. Если добавлен источник или константа расчёта — внести в `sources.yaml` с происхождением.
4. Если менялась выборка данных — отдельно перепроверить путь `historical_forecast` на утечку после `as_of`.
5. Если добавлены зависимости — обновить файл зависимостей и сборку.
6. Обновить README и описание метода тем же изменением, а не отдельной задачей «потом».
